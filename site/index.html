Bakeoff

When several pull requests fix one issue, Bakeoff opens a Switch room for that issue

Coding agents make pull requests cheap. Reading five of them is not. Today, maintainers re-read every PR against the issue, over days, and contributors whose PRs lose usually get silence or a one-line close. Bakeoff turns that into one sitting in one chat room.

How it works

1

Code opens the room

Bakeoff sees two or more open PRs on the same issue and creates a contest room with a matrix: one column per PR, showing CI status and scope.

2

Two readers read

Claude Code and OpenCode each read every diff against the issue's checklist and record verdicts with evidence. Code marks where they agree or split.

3

People talk

Maintainers and contributors ask questions and discuss in the room. Readers can re-read and update their verdicts with new evidence.

4

A maintainer picks

One named maintainer says which PR wins. Switch requires human approval. Code facts—not opinions—decide what passed.

5

It lands on GitHub

The winning PR merges with a note naming who picked it. Every other PR gets a thank-you listing what it missed, then closes.

Code decides the facts, two readers decide the checklist, a maintainer decides the winner.

Why this matters

Bakeoff separates three decisions: what passes (code runs tests), what's complete (two independent agents read), and who wins (one named person). Nobody guesses. Contributors know why their PR didn't win. Maintainers get a written record of two independent readings. The contest is decided once.

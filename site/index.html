Bakeoff

When several pull requests fix one issue, Bakeoff opens a Switch room for that issue.

Two agents from different vendors check every PR against the issue’s own checklist, GitHub’s CI decides what passed, and one maintainer picks the winner by name before anything is posted.

See the demo contest Read the code on GitHub

How a contest runs

Code decides the facts, two readers decide the checklist, a maintainer decides the winner.

Select a step to see the room at that point.

Why it exists

During this hackathon, Switch’s own repository had 349 open pull requests, and many issues had five to ten people claiming them. Coding agents make a pull request cheap. Reading five of them against one issue is not.

Today a maintainer re-reads every PR against the issue, over days, and the people whose PRs lose usually get silence or a one-line close. Bakeoff turns that into one sitting in one room, and every PR that loses gets a note naming the checklist item it missed.

When it goes wrong

The rules that matter live in code and in Switch’s settings, so an agent can’t talk its way past them.

A PR says its tests pass, and CI failed
The cell stays red with “claims pass, CI failed”, and merge_pick refuses a PR whose CI hasn’t passed. Nobody in the room can overrule GitHub.
The readers disagree
The matrix marks the item SPLIT, and the readers point the maintainer at it.
Someone picks a decided contest
Refused, naming who decided and when. Nothing is posted.
Someone who isn’t a maintainer tells the merge agent to merge
Switch’s addressing policy doesn’t deliver the message.
GitHub refuses the merge
The pick is undone and the contest stays open.
A decline note fails to post
The tool says which one, and the pick stays recorded.

What Switch does here

Each part of a contest leans on one Switch feature. Only the merge agent’s tools can merge, and each agent’s name comes from its own environment, never from a tool argument.

Room templates
The watcher opens one room per contest from a YAML template, with its instructions, roles, members and a contest document.
Kickoff and addressing policy
The kickoff wakes both readers. The merge agent takes instructions only from maintainers.
Roles with exclusive leases
Checker, second opinion and merger each have one holder at a time, so no agent both judges and merges.
Agents from different vendors
Claude Code reads beside OpenCode, and the matrix shows where they split, so no model marks its own homework.
Approval cards
merge_pick is the one tool the merge agent can’t run without a person. Switch posts Allow once or Decline in the room and records who answered.
Slack bridge
The room is a Slack channel, and each agent posts under its own name.

The demo contest

Issue #1 asks for a bakeoff summary command. Claude Code, Kimi Code, Pi and OpenCode got the same prompt, and their work became four real pull requests. All four pass CI. They differ on the checklist and the scope, which is what the room reads for.

Open the demo contest, issue #1

Run it yourself

You need a Switch server with the agent controller, Slack or the bundled Mattermost, uv, and a GitHub token that can read and write the repository you watch. After setup, one pass of the watcher:

uv run bakeoff watch OWNER/REPO --once

To print the matrix in a terminal, without Switch:

uv run bakeoff matrix OWNER/REPO ISSUE
